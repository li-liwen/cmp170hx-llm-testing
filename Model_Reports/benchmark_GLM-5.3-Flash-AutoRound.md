## Executive Summary

This report evaluates glm-5.3-flash inference on a 4xCMP 170HX (GA100, sm_80, unlocked 64GB) deployment, prioritizing interactive user experience—low time-to-first-token, low per-token latency, and healthy per-user streaming—over maximum aggregate throughput. Under that priority, the recommended operating point is concurrency c=2, which is interactive-optimal by TTFT/TPOT p99 while sustaining roughly 35.5 tok/s per user, and single-stream decode is highly stable, with the Decode Stress Test posting the best mean TPOT at 22.85 ms. Peak aggregate throughput was reached in the Short Context Throughput scenario at 143.57 tok/s, but this is secondary: at higher concurrency levels, queueing causes TTFT tails to grow sharply and per-user rates to collapse, so capacity beyond the sweet spot should be treated as a batch-throughput option rather than an interactive one.

- PP/TG (derived): 1827.2 / 43.2 tok/s

---

**Interpretation:**

- A TTFT of ~1.1 s on a 2,048-token prompt is almost entirely prefill processing (~1.8k tok/s derived prefill rate), which is the expected shape at concurrency 1 — with no queueing component, first-token latency here is driven directly by prompt length, so shorter prompts would shrink the wait nearly proportionally.
- The TTFT distribution is very tight: p99 is only ~5% above the mean and the median sits essentially at the mean, meaning prefill latency was highly repeatable across all 20 prompts with no stragglers or outliers.
- TPOT of ~23 ms works out to ~43 tok/s of single-stream decode, and mean/median/p99 agree to within hundredths of a millisecond — an exceptionally steady decode loop with no visible jitter, stalls, or degradation.
- ITL matching TPOT confirms that smooth cadence holds across the entire 512-token generation, and decode speed appears insensitive to the context growing as tokens are emitted — users should experience uniform streaming rather than bursty output.
- The run-average output throughput (~40 tok/s) trails the TPOT-implied decode rate (~43 tok/s) because wall-clock averaging charges each request's ~1.1 s prefill against output tokens; the implied per-request time (~1.1 s prefill + ~11.9 s decode ≈ 13 s, × 20 requests) accounts for the full ~259 s run almost exactly, leaving essentially no idle gap between requests.
- Peak output throughput (44 tok/s) aligning with the decode-derived rate reinforces that generation sustains its cadence once started; elapsed time per request is dominated by the decode phase (~12 s) rather than prefill (~1.1 s), so output length—not prompt size—is what determines how long a user waits for completion.
- As a no-batching baseline, this scenario represents the latency floor for this deployment: TTFT here is pure prompt cost and TPOT is uncontended decode, so any future increase in concurrency should be judged against how much of this TTFT and TPOT consistency it preserves.

## Recommendations

- Use c=2 (interactive-optimal by TTFT/TPOT p99; per-user 35.5 tok/s) for interactive UX.
- Cap live session concurrency at the c=2 sweet spot and place excess arrivals in a waiting/queueing tier; past this point, TTFT and TPOT p99 tails degrade and per-user throughput erodes below the 35.5 tok/s figure, so admitting more concurrent users buys aggregate throughput at the cost of interactive responsiveness.
- Treat TTFT and TPOT p99 as the primary health signals: if either drifts above the levels seen at c=2, hold new admissions or reroute rather than letting more requests contend in the active set — p99 recovers faster via admission control than via waiting out a saturated pool.
- Keep interactive and batch/offline traffic in separate pools: batch jobs should run under an explicitly throughput-oriented concurrency policy and tolerate worse TTFT/TPOT, and mixing them into the interactive pool will contaminate p99 even when average throughput looks healthy.
- For the batch/offline trade-off only: deliberately push concurrency higher on batch lanes to collect the aggregate throughput gains observed under load, but label those runs as non-latency-sensitive and never present their throughput as interactive capacity.
- Scale out, not up: once interactive demand exceeds what a single 4-GPU node serves cleanly at c=2, add replicas behind a request router so each instance stays inside its TTFT/TPOT envelope, instead of driving one node past the measured sweet spot.
- Re-run the benchmark whenever prompt/context profile or serving configuration changes: the c=2 optimum and the 35.5 tok/s per-user figure were established under the tested workload, so treat them as valid only until inputs or stack settings shift materially.
